# B10 booking: implementation plan

Spec: `docs/superpowers/specs/2026-10-06-b10-booking-design.md` (approved by Fabian 2026-10-06; only acceptance holds the time).

## Steps (test-first)

1. `BookingIntegrationTest` with the scenarios from spec section 4, failing.
2. Availability facade: `hold(artistId, from, to, bookingId)` (covering free time turns booked, or a new booked slot when nothing overlaps; `false` on a conflict) and `isBooked(artistId, from, to)`.
3. Migration `V11__booking.sql` (V10 is taken by B12 in PR #18): `booking` + `booking_step`.
4. Module `booking`:
   - root: `Bookings` facade (`venueHasAcceptedBetween`, `find`), `BookingStatus`, `BookingParty`, `BookingInfo`, events;
   - `domain`: `Booking` (status as of now: unanswered 72 h or started = EXPIRED, accepted and ended = COMPLETED), `BookingStep`, `BookingTerms`, `BookingErrors`;
   - `application`: `BookingService` (request, apply, counter, accept, decline, withdraw, cancel, get, list, store expiry/completion), `BookingView`, `BookingJob` (every 15 min);
   - `infrastructure`: `BookingRepository`;
   - `api`: `BookingController`, `BookingDtos`.
5. Error texts in `messages_pl/en.properties`.
6. `./gradlew test` (incl. `ModularityTest`), `pnpm api:generate`, commit `schema.d.ts`, CLAUDE.md bullet.

## Defaults taken while planning

- Names in history: the step records the party (artist, venue, system) and whether it was the viewer; accounts have no display names yet, so no person's name.
- Booking keeps a snapshot of the stage name and venue name, so a later unpublished profile does not blank the booking; links (slugs) come from published profiles only.
- A venue's proposal must lie in the artist's free time unless the booking came from the venue's own listing; an artist's proposal must only avoid their booked time.
- Booking notifications are wired once B12 (PR #18) is merged.

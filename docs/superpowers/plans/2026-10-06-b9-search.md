# B9 search: implementation plan

Spec: `docs/superpowers/specs/2026-10-06-b9-search-design.md`.

## Approach

`search` owns no tables. Each owning module answers "candidates near a point" from its own PostGIS column
(nearest first, at most 1000), applying the filters it can check on its own data; `search` joins across modules,
applies cross-module filters (published author, free time, travel radius), sorts by distance then name and pages in
memory. 1000 candidates is plenty for one city in the MVP; past that, paging moves into SQL.

## Steps

1. `SearchIntegrationTest` (test-first): radius and order, each filter, free time (slot, rule, booked), "will travel",
   drafts and inactive listings hidden, own location as centre, missing location, paging, signed-in only.
2. Facades:
   - `location.Nearby` gains the stored point and town.
   - `artist.ArtistProfiles.findPublishedCards(ownerIds)` -> `ArtistCard` (genres, rate, travel radius, avatar id).
   - `venue.VenueType` moves to the venue root; `Venues.findPublishedWithin(VenueSearch)` -> `VenueCard` with
     distance (native query on `venue.point`); `Venues.findPublishedCards(ids)` for listing authors.
   - `listing.Listings.findActiveWithin(ListingSearch)` -> `ListingCard` with distance (native query on
     `listing.point`).
3. `search`: `SearchService` + `SearchController` (`/api/v1/search/artists|venues|listings`, `isAuthenticated()`),
   `SearchErrors` (`SEARCH_LOCATION_REQUIRED`, `SEARCH_CENTER_INCOMPLETE`, `SEARCH_TIME_INVALID`), messages PL/EN.
4. `./gradlew test` (incl. `ModularityTest`), `pnpm api:generate`, CLAUDE.md bullet, PR.

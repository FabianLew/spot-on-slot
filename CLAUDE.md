# Spot On Slot: working rules

Read `docs/architecture.md` before larger changes. Decisions there are agreed with the product owner; do not change the stack without asking.

## Backend (`apps/backend`)
- Base package `pl.spotonslot`; each top-level package is a Spring Modulith application module with a `package-info.java`.
- Module layout: `api` (controllers, DTOs), `application` (services/use cases), `domain` (entities, rules), `infrastructure` (repositories, integrations).
- Other modules may use only a module's root package (facade, public types) and its events. Cross-module side effects go through application events (`@ApplicationModuleListener`), not direct calls into internals.
- `shared` is an open module for cross-cutting code only (security, errors, web config). No business logic there.
- Schema changes only through Flyway migrations in `src/main/resources/db/migration`; JPA runs with `ddl-auto: validate`. Store times as `timestamptz` (UTC).
- `./gradlew test` must pass, including `ModularityTest`. Integration tests use Testcontainers (`TestcontainersConfiguration`, PostGIS image).
- REST endpoints live under `/api/v1/...`.
- Errors (`shared.error`): throw `DomainException` subclasses (`NotFoundException`, `ConflictException`, `BusinessRuleException`, `InvalidRequestException`) with a module-specific UPPER_SNAKE `code`. Responses are RFC 9457 `application/problem+json` with `code`, `requestId`, `errors` (validation only). Texts live in `messages_pl/en.properties` as `error.<CODE>.title|detail`; untranslated codes fall back to the generic text for the status.
- Database constraint violations: catch `DataIntegrityViolationException` in the module and rethrow a `ConflictException` with a module code; left untranslated, the shared handler renders it as a generic 500. Anonymous callers get 401 (not 404) for unknown paths: security runs before routing, by design.
- Paging (`shared.paging`): `PageQuery` + `PageResponse`, 0-based, `size` <= 100, `sort=field,asc|desc` checked against a per-endpoint allowlist.
- Entities (`shared.persistence`): extend `BaseEntity` (UUID v7 `id`, `createdAt`, `updatedAt`, `version`). Migration columns: `id uuid primary key, created_at timestamptz not null, updated_at timestamptz not null, version bigint not null`.
- Web (`shared.web`): `RequestIdFilter` (`X-Request-Id`, echoed in logs and errors); CORS via `spotonslot.cors.allowed-origins`. OpenAPI documents the problem schema automatically.
- Lombok for boilerplate: `@Getter`/`@Setter`, `@RequiredArgsConstructor` for constructor injection, `@NoArgsConstructor(access = PROTECTED)` on entities, `@Slf4j` for loggers. Don't hand-write getters, setters or plain constructors. Entities never use `@Data`, `@EqualsAndHashCode` or `@ToString` (lazy loading); DTOs stay Java `record`s. `lombok.config` copies `@Qualifier`/`@Value` from fields to generated constructors.
- Events: cross-module side effects use `@ApplicationModuleListener` (e.g. `WaitlistConfirmationRequested` in `waitlist` -> confirmation e-mail in `notification`); failed listeners stay in the Modulith event registry and are retried.
- Mail: `spring-boot-starter-mail`; dev uses Mailpit (SMTP `localhost:1025`, UI `localhost:8025`, from `docker compose`). Prod env: `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM`, `LANDING_BASE_URL` (confirmation links). Mail is excluded from `/actuator/health`.
- Identity (`identity`): access token = JWT HS256 (15 min, claims `sub`, `role`, `iss`) via the OAuth2 resource server; refresh token = opaque value in HttpOnly cookie `sos_refresh` (`Path=/api/v1/auth`, 30 days, rotated on every refresh, reuse revokes the family). `/api/v1/auth/**` is public, everything else needs `Authorization: Bearer`. Passwords use PBKDF2 (`DelegatingPasswordEncoder`); BCrypt would cut passwords at 72 bytes. Endpoints that take an e-mail answer the same for known and unknown addresses. Prod env: `JWT_SECRET` (>= 32 bytes), `WEB_BASE_URL` (links in account mails).
- Media (`media`): browser PUTs straight to S3-compatible storage through a presigned link (`POST /api/v1/media/uploads`), then `.../complete` checks the real format and pixel count, applies EXIF orientation and stores WebP variants 320/800/1600 px without metadata; the original is deleted. Variants are public under `MEDIA_PUBLIC_BASE_URL`. Storage is Cloudflare R2 in prod and S3Mock locally (`docker compose`) and in tests (`TestcontainersConfiguration`). Prod env: `MEDIA_ENDPOINT`, `MEDIA_BUCKET`, `MEDIA_ACCESS_KEY`, `MEDIA_SECRET_KEY`, `MEDIA_PUBLIC_BASE_URL` (optional `MEDIA_PRESIGN_ENDPOINT`, `MEDIA_REGION`); the bucket needs a CORS rule allowing PUT from the web origin. In the web app upload with `uploadImage(api, file)` from `@spot-on-slot/api-client` and `ImagePicker` from `@spot-on-slot/ui`.
- Location (`location`): users set their location from the browser or by picking a suggestion from `GET /api/v1/locations/search` (Photon geocoder behind the `Geocoder` interface; the backend proxies it, browsers never call it). `PUT /api/v1/locations/me` snaps the point to a 0.01° grid (~1 km) before anything else sees it and names the town by reverse geocoding that point; the exact point is never stored. The PostGIS `point` column is generated from `latitude`/`longitude`; other modules query "who is within X km" through the `Locations` facade (`findWithin` gives the stored point, town and distance); only search exposes those approximated points. Tests use `PhotonStub` (in `TestcontainersConfiguration`); the public `photon.komoot.io` is dev only, prod needs `LOCATION_GEOCODER_URL`. A failing dependency throws `ServiceUnavailableException` (503).
- Artist (`artist`): one profile per ARTIST account (`/api/v1/artists/me`, `hasRole('ARTIST')`), saved whole with `PUT` (omitted lists = empty, omitted `slug` keeps the address). The slug comes from the stage name (`shared.text.Slugs`: Polish letters folded, numbered on collision, reserved words). A profile is a draft until `POST .../publish`, which needs a stage name, a genre, a main photo and a location (`missingForPublication` lists the rest). Published profiles are public at `GET /api/v1/public/artists/{slug}` (`/api/v1/public/**` is open, read-only) without the real name or coordinates. Photos are media ids checked through the `MediaLibrary` facade, and `MediaDeleted` removes them from profiles. The town comes from `Locations.findForUser`. Other modules use `ArtistProfiles`. Rates are in grosze (PLN). `artist.Genre` is the genre catalogue other modules (venue, later listings and search) reference.
- Venue (`venue`): a VENUE account can be in up to 10 venue teams (`VenueRole` OWNER or MANAGER); `POST /api/v1/venues` makes the creator owner, `GET /api/v1/venues/mine` lists them. Anyone outside a venue's team gets 404 for it; owner-only actions (publish, delete, team) give managers 403 `VENUE_FORBIDDEN`, and the last owner cannot be removed. The address is public and its point exact (business data): a point picked from `GET /api/v1/locations/search` wins, otherwise `Locations.geocodeAddress` looks it up on save (no match = no point = cannot publish). Invitations go by e-mail (`VenueInvitationSent` -> `notification`, link `WEB_BASE_URL/venue-invitation?token=`, 7 days, token hashed, accepted through `POST /api/v1/venues/invitations/accept` by the VENUE account with that address). New photos must belong to the person saving. Public at `GET /api/v1/public/venues/{slug}` without the team. Other modules use `Venues`; e-mails of accounts come from the `identity.Accounts` facade.
- Availability (`availability`): an artist's own calendar at `/api/v1/availability/me` (`hasRole('ARTIST')`, needs an artist profile) holds FREE slots (30 min to 24 h, may cross midnight) and weekly rules (days + local start time + length, `valid_from`/`valid_until`, expanded in the rule's `time_zone`, for now always Europe/Warsaw, so a 21:00 rule stays 21:00 across the clock change). A day with nothing is unavailable. One rule date can be skipped/restored (`DELETE`/`PUT .../rules/{id}/dates/{date}`). Nothing may overlap (409 `AVAILABILITY_OVERLAP`, checked under a per-artist advisory lock), time that has started cannot change, limits: 20 rules, 500 future slots, rules expand 366 days ahead, reads cover at most 92 days. Published artists' calendars are public at `GET /api/v1/public/artists/{slug}/availability` (times and status only). Other modules use the `Availability` facade (`isFree`, `freeAmong`, `occupy` turns free time BOOKED for a booking id, a rule date becoming its own booked slot; `release` frees it again).
- Listing (`listing`): "Jestem wolny" from an ARTIST (`/api/v1/listings/mine`, needs a published profile; its time must be free in the calendar per `Availability.isFree`, no two active listings of an artist overlap) and "Szukam artysty" from a venue's owner or manager (`/api/v1/venues/{venueId}/listings`, published venue only; several per evening allowed). Authors edit and close by id (`PUT /api/v1/listings/{id}`, `POST .../close`); a listing of another artist or of a venue outside the caller's teams is 404. Statuses ACTIVE, CLOSED, EXPIRED, FILLED (set by booking through `Listings.markFilled`); none can be reopened. An active listing whose time has started reads as EXPIRED at once and `ListingExpiryJob` stores that every 15 min; `availability.AvailabilityChanged` (slot/rule changed or removed, date skipped or booked) expires artist listings whose time is no longer free. Times 30 min to 24 h, at most 365 days ahead; limits 20 active per artist, 30 per venue; descriptions 500 (artist) / 1000 (venue); prices in grosze. City and point are copied on posting (artist: the approximated point via `Locations.findPointForUser`, venue: exact), so moving later does not move old listings. Public at `GET /api/v1/public/listings/{id}` while active and the profile is published. `ListingPublished` is for notifications (B12); other modules use `Listings`.
- Search (`search`): `GET /api/v1/search/artists|venues|listings` for signed-in users of any role. Centre `lat`/`lng` (both or neither; neither = the searcher's own location, none = 400 `SEARCH_LOCATION_REQUIRED`), `radiusKm` 1–200 (default 50), `genres` (any of), `page`/`size` <= 100, no `sort`: always nearest first, then by name (Polish collation). Artists: `from`/`to` (free for the whole time per `Availability.freeAmong`, at most 24 h), `budget` (rate "from" within it, no rate matches), `willTravel` (distance <= their travel radius). Venues: `types`. Listings: `kind`, `from`/`to` (overlapping, at most 366 days), `budget` (seeking: top amount reaches it; free: bottom amount within it; none matches). `search` owns no tables: each module returns up to 1000 nearest candidates filtered on its own data (`Locations.findWithin`, `Venues.findPublishedWithin`, `Listings.findActiveWithin`), `SearchService` adds cards (`ArtistProfiles.findPublishedCards`, `Venues.findPublishedCards`, `MediaLibrary`), drops unpublished authors and pages in memory. Artists' points are the approximated ones, venues' exact; no real names.
- Notification (`notification`): in-app notifications (`/api/v1/notifications`: newest first, `unread-count`, `{id}/read`, `read-all`, kept 90 days) and settings (`GET`/`PUT .../preferences`; no row = defaults). B12 sends one type, `NEARBY_LISTING`, from `listing.ListingPublished`: a venue's "Szukam artysty" goes to published artists whose travel radius (or own radius setting, 5–200 km) reaches it, an artist's "Jestem wolny" to the teams of published venues within the listing's travel radius and the person's radius (default 50 km), one alert per person (nearest venue); a shared genre is needed (setting, else profile/venue genres), artists with booked time overlapping it (`Availability.bookedAmong`) are skipped, at most the 1000 nearest candidates. The payload (jsonb) freezes what is shown. Every stored notification publishes `NotificationCreated`, the single fan-out point for channels (e-mail now, WebSocket/push later; can be externalized to a broker via spring-modulith-events-amqp, no RabbitMQ in the MVP: Fabian's choice). Alert e-mails: at most 5 per person per Warsaw day, skipped once the listing ended, link `WEB_BASE_URL/o/{id}`, unsubscribe link `WEB_BASE_URL/unsubscribe?token=` + `List-Unsubscribe` one-click headers; `POST /api/v1/public/notifications/unsubscribe` (the only write under `/public`) switches e-mails off. Account e-mails (verification, reset, invitations) ignore settings.
- Profiles: `dev` (default), `prod`, `test`.
- Tests: use `@IntegrationTest`; test-only tables go in `src/test/resources/db/testmigration`; test controllers under `/test/...` must be `@Hidden`.

## Frontend (`apps/web`, `apps/landing`, `packages/*`)
- pnpm workspaces + Turborepo. Internal packages are consumed as TypeScript source (`transpilePackages`).
- Call the backend only through `@spot-on-slot/api-client`; never hand-write request/response types. After API changes run backend tests, then `pnpm api:generate`, and commit `schema.d.ts`.
- Colors/spacing come from `@spot-on-slot/design-tokens`; keep `src/index.ts` and `src/theme.css` in sync.
- UI copy is Polish by default; keep i18n in mind (`SUPPORTED_LOCALES`).
- Navigation: `apps/web/src/components/navigation/nav-items.ts` is the single source for the sidebar, bottom tabs and the "Więcej" sheet. Entries are plain serializable data: `icon` is a `NavIconName` string resolved client-side in `nav-icons.ts`; never put components or functions in them. Adding a section = an entry in `nav-items.ts` + (new icon → `NavIconName` + `nav-icons.ts`) + a page under `src/app/(app)/` + `nav.*` keys in both message files.
- i18n (`apps/web`): next-intl without routing; locale from cookie `NEXT_LOCALE` → Accept-Language → `pl`. Copy lives only in `apps/web/messages/{pl,en}.json` (key parity test, typed keys). Switch locale with the `setLocale` server action.
- Theme: next-themes, class-based; light/dark tokens in `@spot-on-slot/design-tokens` (`index.ts` and `theme.css` are kept in sync by a test). Palette is black/gray + red accent, a placeholder until the brand book; danger text always comes with an icon.
- `packages/ui`: shadcn-style components; no `next-intl`/`next` imports, text comes via props; files using hooks/context need `"use client"`.
- API in `apps/web`: use `api` from `src/lib/api.ts` (wraps `@spot-on-slot/api-client`, sends Accept-Language); `unwrap`, `toApiProblem` and `ApiProblemError` come from `@spot-on-slot/api-client`; show query errors with `ApiErrorState`; mutation errors toast automatically unless the mutation sets `meta: { handlesErrors: true }`.
- Session (`apps/web`): access token only in memory (`src/lib/api.ts`), restored after reload through `refreshSession()` (one shared request, since the refresh token rotates); the api-client retries a 401 once after a refresh and sends `/api/v1/auth/*` with `credentials: "include"`. `useSession()` from `components/session/session-provider.tsx`; `AuthGate` in `(app)/layout.tsx` sends anonymous users to `/login?next=` (pass `next` through `safeNext`). Account pages live in the `(auth)` route group.
- Onboarding (`apps/web`, W2): `/onboarding` in the `(onboarding)` route group (own layout, no sidebar) holds the artist and venue wizards from `components/onboarding`. Every step saves the whole profile at once (`artistRequest`/`venueRequest` merge the patch with what is stored) and a returning user resumes at the first step `missingForPublication` points to. `OnboardingGate` in `(app)/layout.tsx` sends ARTIST/VENUE accounts without a profile to the wizard unless they chose "Uzupełnię później" (per-user flag in `localStorage`, `skip.ts`); the dashboard shows `ProfileReminder` until the profile is published. Genre and venue type lists are in `options.ts`, names in `genres.*`/`venueTypes.*`. `packages/ui` has `Stepper` and `ChoiceChips` for this; `LocationPicker` hides the device button without `onUseDevice`. Nullable backend fields arrive as `null`, so check them with `!= null`.
- Artist profile (`apps/web`, W3): `/profile` shows the own profile with publish/unpublish and copy link, `/profile/edit` is one form (`components/artist/profile-form.tsx`, values <-> request in `profile-form-values.ts`; the slug is sent only when changed, rates are typed in zł and sent in grosze, skill 0 = not set). `ArtistProfileView` renders both the preview and the public page `/a/[slug]` (server-rendered outside the `(app)` group, no sign-in, `noindex` until launch, data via `findPublicArtist` in `src/lib/public-profiles.ts`, which reads `API_URL` and falls back to `NEXT_PUBLIC_API_URL`). The location is its own resource (`ArtistLocationPicker`, saved at once). `packages/ui` has `TagInput` and `SkillSlider`.
- Venue profile (`apps/web`, W4): a VENUE account's `/profile` shows one venue (`?venue=id`, else the oldest) with a switcher and "Dodaj lokal" (`/onboarding?new=venue`, the wizard's `fresh` mode, up to 10). Edit at `/profile/venues/[id]/edit` (`components/venue/venue-form.tsx`, values <-> request in `venue-form-values.ts`; the address sends a point only from a picked suggestion, `VenueAddressFields` is shared with the wizard), team at `.../team`. Owner-only actions are hidden or disabled by `venue.role`. The invitation link `/venue-invitation?token=` lives in the `(onboarding)` group, so `OnboardingGate` does not catch invited accounts without a venue. Public page `/v/[slug]` (`VenueProfileView`, `findPublicVenue`) mirrors `/a/[slug]`; both use `PublicShell`. Own-profile state and actions come from `components/profile/status-bar.tsx` (`profileStatus.*`); the venue list cache is updated with `storeVenue`/`dropVenue`.
- Calendar (`apps/web`, W6): `/calendar` (`components/calendar`) shows an ARTIST's availability by month (`MonthCalendar` with `selectAny`/`isBooked`, day panel beside it) or week (seven day columns, a list per day, no hour grid: Fabian's choice); other roles see a note. All day/time math goes through `warsaw-time.ts` (Europe/Warsaw, independent of the browser zone; days are `YYYY-MM-DD` strings). `SlotDialog` adds or edits a single slot or, with "Powtarzaj co tydzień", a weekly rule (an end at or before the start means the next day). Skipped rule dates come from `rule.skippedDates` and are shown crossed out with "Przywróć" (`entriesByDay`). Booked and started time is read-only. Writes invalidate `["availability"]`. The artist profile view shows `NextFreeSlots` (first free time per day, up to 6 within 60 days): the own preview from `/me`, `/a/[slug]` from the public endpoint via `findPublicAvailability`.
- Listings (`apps/web`, W7): `/listings` (`components/listings`) lists the own listings with an Aktywne/Zakończone filter (`useOwnListings`; a VENUE account picks a venue with `?venue=`, `?add=1` opens the dialog); posting needs a published artist profile or venue. `ListingDialog` posts, edits and copies ("Dodaj podobne"): artists pick free time from the calendar (`PICK_DAYS` = 90, time already announced is disabled; the calendar day panel's "Ogłoś" opens it on that time and marks announced time "Ogłoszony"), venues type date and hours (an end at or before the start means the next day); genres, money and travel default from the profile, amounts typed in zł are sent in grosze (`listing-form-values.ts`). Writes invalidate `["listings"]`, calendar writes too (they can expire listings). Public page `/o/[id]` (`ListingView`, `findPublicListing`, `PublicShell`, `noindex`); keep `listing-time.tsx` and `listing-view.tsx` free of `"use client"` code, since the server renders them.
- Forms: `Form` from `@spot-on-slot/ui` + a zod schema whose messages are `validation.*` keys (translated via `translateFormError`); `applyServerErrors` and `translateFormError` come from `@spot-on-slot/ui`; `applyServerErrors(form, problem)` maps backend `errors[]` to fields or `root.server`.
- Tests: Vitest + Testing Library in `packages/ui`, `packages/design-tokens`, `packages/api-client`, `apps/web`, `apps/landing`.
- Before pushing: `pnpm lint && pnpm typecheck && pnpm test && pnpm build`.
- Landing (`apps/landing`): locale-prefixed routing (`/pl`, `/en`) via `src/i18n/routing.ts` + `src/proxy.ts`, `localePrefix: always`, no locale cookie; `/` redirects by Accept-Language, unknown first segments 404.
- Landing copy lives only in `apps/landing/messages/{pl,en}.json`.
- Landing hero: config in `src/components/hero/hero.config.ts`; the hero reproduces Fabian's prompt, so do not restyle its classes or animations.
- Landing env: `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_PRIVACY_CONTROLLER`, `NEXT_PUBLIC_PRIVACY_EMAIL`; with `LANDING_ENV=production` the build fails without any of them (see `apps/landing/.env.example`).
